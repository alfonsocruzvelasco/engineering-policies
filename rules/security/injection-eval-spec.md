# Prompt Injection Evaluation Spec

**Status:** Authoritative
**Last updated:** 2026-07-18
**Owner:** Security policy owner

## 1) Purpose

Define a repeatable prompt-injection evaluation harness for AI-assisted workflows, including ChatGPT sessions, so security hardening is measured continuously instead of only by manual review.

This specification operationalizes the policy intent from:
- `rules/security-policy.md` (Prompt Injection Defense, Verification Gates)
- `rules/ai-workflow-policy.md` (Prompt Injection Defense, ChatGPT Untrusted Content Isolation)

## 2) Threat model scope

The harness must cover:
- **Direct injection:** malicious instructions in user-visible prompt text
- **Indirect injection:** malicious instructions embedded in retrieved/untrusted content
- **Instruction hierarchy override attempts:** fake system/developer directives
- **Data exfiltration attempts:** requests for secrets, credentials, hidden prompts
- **Tool abuse escalation attempts:** autonomous destructive operations

Out of scope for this v1:
- image-only payloads
- multimodal steganography
- browser DOM renderer exploits

## 3) Required artifact layout

```text
security-evals/
  attack-corpus/
    direct-injection.jsonl
    indirect-injection.jsonl
  baselines/
    injection-baseline.json
  run_injection_evals.py
```

## 4) Corpus schema (JSONL)

Each line is one test case with required keys:
- `id`: stable unique identifier (`pi-direct-001`, etc.)
- `attack_type`: `direct` or `indirect`
- `category`: one of:
  - `instruction-override`
  - `fake-authority-tags`
  - `data-exfiltration`
  - `tool-abuse`
  - `policy-bypass`
  - `obfuscated-payload`
- `severity`: `low` | `medium` | `high` | `critical`
- `prompt`: adversarial input payload
- `expected_behavior`: one of:
  - `refuse_and_flag`
  - `summarize_as_data_only`
  - `require_human_confirmation`
- `notes`: short rationale

## 5) Mandatory coverage minimum

- At least 12 total cases
- At least 2 cases per required category
- Both `direct` and `indirect` attack types represented
- At least 2 `critical` severity cases

## 6) Evaluation modes

### Mode A: Static (required in hooks and CI)

Validates:
- corpus schema
- coverage minimums
- duplicate ID absence
- baseline file presence and schema

### Mode B: Runtime scoring (required for model recertification)

Input:
- model responses (generated by approved workflow)

Output:
- pass/fail per test case
- score by category and attack type
- overall pass rate
- baseline comparison result

## 7) Merge gate thresholds

For runtime scoring:
- overall pass rate must be `>= baseline.min_pass_rate`
- no `critical` case may fail
- no category may regress by more than `baseline.max_category_regression`

Default baseline values are stored in:
- `security-evals/baselines/injection-baseline.json`

## 8) ChatGPT-specific hardening requirements

When evaluating ChatGPT models:
- run scenarios under `rules/ai-workflow-policy.md` §8.1 isolation controls
- no connectors/apps during untrusted-content scenarios unless explicitly approved exception exists
- do not include real secrets or production identifiers in prompts
- capture model/version metadata for every run

## 9) Governance requirements

- Any threshold change requires a `CHANGELOG.md` entry
- Any failed `critical` case blocks merge until resolved or exception recorded in `rules/security-exceptions.md`
- New prompt-injection incidents must produce at least one new corpus case within 7 days
